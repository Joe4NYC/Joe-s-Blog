# 寫文章範本

給人或 AI 產出 `src/content/blog/*.md` 用的規格。照這份寫出來的檔案，
`npm run frontmatter:check` 會過、Astro build 不會掛、後台編輯器也讀得懂。

最下面有一段可以直接複製貼給 AI 的提示詞。

---

## 1. 骨架

````markdown
---
title: "文章標題"
date: "2026-09-08T21:30:00+08:00"
description: "一到兩句話說明這篇在講什麼，會出現在文章列表和搜尋結果。"
draft: false
categories:
  - "分類名稱"
tags:
  - "標籤一"
  - "標籤二"
---

開頭一到兩段，講清楚這篇要解決什麼問題、讀者能拿到什麼。

<!-- more -->

## 第一個小節

正文。

## 第二個小節

正文。
````

檔名用 `標題_YYYYMMDD.md`，例如 `交換第一週_20260901.md`，網址就是
`/blog/交換第一週_20260901/`。檔名不能有斜線，副檔名必須是 `.md` 或 `.mdx`。

---

## 2. Frontmatter 規格

| 欄位 | 必填 | 說明 |
|---|---|---|
| `title` | ✅ | 不能是空字串 |
| `date` | ✅ | 必須是 `YYYY-MM-DDTHH:MM:SS+08:00`，一秒都不能省 |
| `updated` | — | 同上格式。沒改過就整行不要寫 |
| `description` | — | 強烈建議寫。列表摘要與 SEO 描述都吃這欄 |
| `draft` | — | `true` / `false`，不加引號。省略等同 `false` |
| `categories` | ✅ | **最多一個**；`draft: false` 時**剛好一個** |
| `tags` | ✅ | `draft: false` 時**至少一個**；不可重複 |

### 五條會讓 CI 變紅的硬規則

1. **欄位順序固定**：`title` → `date` → `updated` → `description` → `draft` →
   `categories` → `tags`。順序不對，`frontmatter:check` 會判定檔案需要重寫而失敗。
2. **不能有規格外的欄位**。schema 是 `strict` 的，多寫一個 `author`、`cover`、
   `keywords` 都會讓整個 build 掛掉。
3. **字串一律用雙引號**（JSON 風格）。只有 `draft` 的 `true` / `false` 不加引號。
4. **陣列項目縮排剛好兩個空白**，寫成 `  - "值"`。
5. **標籤要先自己轉小寫**。純英數的標籤用連字號不要用空白
   （`side-project` ✅ / `Side Project` ❌ / `Astro` ❌ 要寫 `astro`）。
   中文標籤照常寫，但不要有多餘空白。

> 這幾條不是風格偏好。`scripts/normalize-frontmatter.mjs` 會用固定格式重新序列化
> 每個檔案，CI 拿重寫結果跟原檔比對，只要有一個位元不同就 fail。

## 3. 內文能用的語法

| 想要 | 怎麼寫 |
|---|---|
| 摘要斷點 | `<!-- more -->`，列表只顯示這行以上的內容 |
| 標題階層 | 從 `##` 開始。`#` 已經被 frontmatter 的 `title` 佔用了 |
| 圖片 | `![這裡的文字會變成圖片下方的說明文字](/image/資料夾/檔名.webp)` |
| 程式碼 | ` ```ts ` 之類標好語言，明暗主題都會上色 |
| 流程圖 | ` ```mermaid ` 圍籬，前端會即時渲染 |
| 數學 | 行內 `$E = mc^2$`，獨立成塊用 `$$ ... $$` |
| 引用 | `>` 開頭。每行一個 `>` 就會斷行，不用在行尾補兩個空白 |
| 表格 | 標準 Markdown 表格，過寬時手機上會自動變成可橫向捲動 |

圖片放在 `public/image/` 底下，文章裡用 `/image/...` 開頭引用。
**alt 文字會被當成圖說直接印在圖片下面**，所以要寫成一句完整的說明，
不要寫「圖片」「screenshot」這種佔位字。

## 4. 完整範例

````markdown
---
title: "把部落格後台搬上 Cloudflare Workers"
date: "2026-09-08T21:30:00+08:00"
description: "記錄一次把靜態部落格加上寫作後台的過程：為什麼選 Workers、怎麼避免拖慢前台，以及踩到的三個坑。"
draft: false
categories:
  - "記錄"
tags:
  - "cloudflare"
  - "astro"
  - "side-project"
---

靜態部落格最麻煩的地方，是每次想改一個錯字都得開編輯器、commit、等 CI。
這篇記錄我怎麼在不犧牲前台效能的前提下，加上一個能直接在瀏覽器裡寫作的後台。

<!-- more -->

## 為什麼不是再開一台伺服器

最直覺的作法是另外跑一個 Node 服務，但那等於為了一天用不到五分鐘的功能，
養一台要付費、要更新、要監控的機器。

![後台儀表板：左側是導覽，右側是文章與部署狀態。](/image/admin/dashboard.webp)

## 只讓 API 走動態路徑

關鍵設定只有一行——讓靜態資源直接命中 CDN，只有後台 API 才進 Worker：

```jsonc
"run_worker_first": ["/api/*"]
```

這樣前台的 TTFB 完全沒有變化。

## 踩到的三個坑

> 第一個坑花掉的時間，比後面兩個加起來還多。
> 而且回頭看完全可以避免。

1. 密鑰忘了設，Worker 起來但每個 API 都回 500。
2. CI 的 token 權限少給了 Actions，部署一直紅。
3. 圖片路徑寫成相對路徑，本機正常、線上 404。
````
